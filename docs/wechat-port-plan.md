## 二、硬缺口（按阻塞强度排序）

1. **UI 层依赖 DOM，但不是「全部重写」**（原写「100% 依赖、一行都跑不起来」为错估，2026-11-16 实测更正）。
   实测（`tools/_domaudit` 临时脚本，按 2 空格缩进切函数块）：
   - `main.js` **5001 行 / 171 个函数块**，其中真正碰 DOM 的只有 **565 行（11.3%）**，散在 **82 个函数**里；
     触点形态：272 处 `$(id)` 取元素、72 处 `innerHTML`、45 处 `document.*`、20 处 `createElement`。
   - `index.html` 静态结构：201 个 div + 70 个 span + 56 个 button + 2 个 canvas = 329 个元素，
     其中 **16 个 `.overlay` 全屏面板**（立誓 / 战斗 / 商店 / 祭坛 / 回响 / 榜单 / 图鉴 / 结算 / 死亡 /
     心迹 / 路遇 / 门 / 塔心石 / 收藏 / 设置 / 立绘放大）+ 主界面 + HUD。
   - **零 DOM 依赖的模块可以直接搬**（0 处 `document`）：`engine.js`（86KB，全部规则）、`story.js`、
     `data.js`、`achievements.js`、`daily.js`、`challenge.js`、`ads.js`、`devgate.js`、`portraits.js`、
     `wxbridge.js`、`wxwire.js`。
   - **`render.js` 本身就是 canvas**（1714 行，只有 2 处 `document.createElement` 用于离屏缓冲）——
     棋盘 / 光照 / 雾层 / 浮字 / 粒子那一套不用改。

   所以路线 A 的真实形态是「**把 render.js 已有的 canvas 能力扩展到 UI 层**」，不是从零起。
2. **没有小游戏工程壳**：缺 `game.json` / `project.config.json` / 小游戏入口 `index.js`（现在入口是 `index.html`）。
3. **缺开放数据域子域**：好友榜要在子域里用 canvas 画到 `sharedCanvas`，这份代码现在只有「请求/回传」的协议，没有绘制实现。
4. **主体与资质**：小游戏需企业/个人主体 + 游戏自审报告；IAA 无需版号（已写死 IAA，红线 A 级）。
5. **备案域名**（2026-11-12 发现，2026-11-16 提级为第一硬卡点）：B 路线的 web-view 要业务域名校验，
   A 路线的 `wx.request` 也要备案域名——**两条路都卡在同一个 1–20 工作日的外部流程上**，而这一步只有用户能启动。

## 三、两条路线（2026-11-16 已选定 B，见 §七；下表留作对比）

| | A · 小游戏（原生） | B · 小程序 + web-view 嵌 H5 |
|---|---|---|
| 改造量 | UI 层重写成 canvas 自绘，**估 15–25 人日**（2026-11-16 按屏重估，原写「3–5 天」低估 4–5 倍） | 近乎为零，现有 H5 直接塞（壳已备好，填两个值） |
| 关系链 | 可用（开放数据域、托管数据） | **不可用**（web-view 里拿不到小游戏能力）；挑战码降级仍可用 |
| 性能 | 好 | 一般（web-view 多一层） |
| 提审 | 小游戏类目 + 自审报告 | 小程序类目，web-view 需域名白名单与业务域名校验 |
| 结论 | 想要社交红利就走这条 | 只想「微信里能玩」就走这条 |

**建议**：先按 B 走一版「微信里能打开」，把玩家引进来验证留存；留存站得住再投 A。
理由：EXP-01 里关系链红利（7 留 +22%）只在**有量**时才兑现，没量的关系链是零。

### B 路线的隐藏前提（2026-11-12 实测发现）

web-view 只能打开**已配置的业务域名**，配置时要往该域名根目录放一个微信校验文件。
而现在的 H5 挂在 `towermates.app.workbuddy.host`（托管域名，根目录不可写）
→ **B 路线也需要一个自己的已备案域名反代**，卡点从「资质」变成「域名备案 1–20 个工作日」。
代码侧的壳已经备好（`wechat/miniprogram/`），域名到位后填 AppID + 换 H5 地址即可。

## 七、2026-11-16 校准（变体 2 · 阶段转换检查）

**为什么要重读这份盘**：它写于 2026-11-12，此后 4 天 UI 长了约 1600 行（3400 → 5001），
而这份文档里的两个关键数字（「100% 依赖 DOM」「3–5 天」）是当初**看着代码估的、没有量**。
一份用来做决策的盘点，用的是没量过的成本——这正是「阶段判断被错误输入带偏」的典型。

**量出来的三件事**：
1. 依赖面只有 11.3%（见 §二.1），逻辑层与棋盘渲染零改造——**A 路线不是从零写**。
2. 按屏重估：16 个 overlay + 主界面 + HUD ≈ 18 屏，每屏 canvas 重排 0.7–1.2 人日；
   再加通用控件层（按钮 / 列表 / 滚动 / 输入框）3–4 人日、联调 2 人日 → **15–25 人日**。
   原估 3–5 天等于「一天五屏」，只有把 DOM 当翻译、不当布局时才成立。
3. 两条路线卡在同一个东西上：**备案域名**。它不属于设计取舍，属于外部流程（1–20 工作日）。

**据此拍板（自主决策，不挂起）**：
- **路线 B 优先**。理由：①留存数据是本作唯一还缺的验证，B 是唯一能在低成本下拿到真人的路；
  ②A 是 15–25 人日的大工程，在留存未验证前投入＝把最大的赌注押在最不确定的前提上；
  ③挑战码本来就是关系链的降级方案且已写完，B 路线里社交并不「全废」，只是少了「自动读好友榜」。
- **待决策区 ② 收窄成一句用户动作**：「要不要现在启动域名备案」。不再需要用户在 A/B 之间选。
- **A 路线降级为「备案期间的预备」**：不投入 UI 重写，只做 §四那条「切 render/main 边界」的半天活——
  它让两条路都受益（B 路线也能借此把 UI 与逻辑的耦合降一档，将来换壳少踩坑）。

**已知风险（写清，不再反复提）**：若备案迟迟不动，微信版整条线就停在原地；
本地 H5（线上地址）本身不受影响，玩家侧体验没有任何变化。
